# Adoption pack

This page is for the reviewer in a regulated team: security, quality or
regulatory affairs, deciding whether the kit can go into your product. Each
claim on it links to the gate or test that holds it, so you can check the
claim rather than trust it.

**Status, 2026-10-02.** Pre-release. Nothing is on npm yet: the packages
publish as 1.0.0 at milestone M11, and until then they are built from this
repository. Where a figure below depends on that release, it says so.

## Not a medical device

The kit renders a FHIR R4 `Questionnaire` and records the answers as a
`QuestionnaireResponse`. It does not interpret answers, it makes no diagnosis
or recommendation, and it makes no safety claim. It is not a medical device.

- **It scores nothing itself.** A score is computed by a scorer you supply
  ([scoring guide](guides/scoring.md)). The guide's worked example shows the
  mechanism on a demonstration block, and it is not a validated instrument.
- **The instrument is yours.** Its wording, its translation, its licence for
  your use, and any scoring rules come from the instrument's owner, not from
  the kit.
- **Clinical validation is yours.** If the product you build is a medical
  device, the kit is third-party software inside it. Qualifying it under your
  quality system, and validating the product for its intended use, are your
  responsibility. What this page gives you to start from: pinned versions,
  the dependency inventory, the SBOM, the [conformance matrix](conformance/matrix.json)
  with the test behind each row, and the [accessibility record](accessibility.md).

## No PHI, no network

The kit holds answers in memory while the form is open, and hands them to
you. It stores nothing, sends nothing, and reports nothing about its use.

| Claim | Held by |
|---|---|
| `@fhirq/core`, `@fhirq/react` and `@fhirq/themes` make no network request, use no browser storage (`localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API) and send no telemetry (NFR-X-01, X-02, X-03) | A test runs a whole session through the public entry points with every one of those doors replaced by a stub that throws, and fails if one is touched: [`core`](../packages/core/test/safety/no-io.test.ts), [`react`](../packages/react/test/no-io.test.tsx), [`themes`](../packages/themes/test/no-io.test.ts) |
| No source file calls `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` or `sendBeacon`, with one named exception | The [`no-network`](../tools/eslint-rules/src/no-network.js) lint rule, part of `pnpm lint` (NFR-M-06) |
| `@fhirq/element` makes only the requests you configure: one `GET` for its `src`, and value-set expansions if you set `value-set-base` ([element guide](guides/element.md)) | That exception is one file, [`default-resolver.ts`](../packages/element/src/default-resolver.ts) (ADR-0012). A [browser test](../packages/element/test/browser/no-io.test.ts) checks that `fetch` is touched from that file alone, once per request |
| No answer value appears in a diagnostic, an error, a change event, a validation issue or on the console (NFR-X-04) | A [property test](../packages/core/test/property/leak.test.ts) marks every text answer with a sentinel, through ordinary use, a throwing rule and a hydration that rejects every stored answer, and fails if the sentinel shows up in any of them |
| The playground and this site load nothing from anywhere else, and the browser forbids them to connect anywhere (NFR-X-09) | Both are served with a Content Security Policy including `connect-src 'none'`, checked in three browsers: the [playground's privacy spec](../tests/browser/playground-privacy.spec.ts) and the [docs site spec](../tests/browser/docs-site.spec.ts) |

**What does carry answers** is what the kit hands you: the
`QuestionnaireResponse` (also the `detail` of the element's `fhirq-change`
and `fhirq-complete` events), and a saved session's snapshot. Both are
patient data once a patient answers. Where you store them, how you send them
and who may read them are yours to decide and to protect. The kit has no
backend, account or server.

## SBOM

Each published package has a CycloneDX 1.6 SBOM, made by
`@cyclonedx/cyclonedx-npm` over the package as it is packed for npm, not over
this workspace ([`sbom.mjs`](../scripts/sbom.mjs)). Each run of CI's
`Engine gates` job builds them, fails if one names a component outside the
kit, and uploads them as its `sbom` artifact, kept for 90 days. Locally:
`pnpm build && pnpm build:sbom` writes them to `reports/sbom/`. The output is
reproducible, so two runs over the same commit give identical files.

Today each SBOM names at most one component: `@fhirq/react` and
`@fhirq/element` name `@fhirq/core`, and `@fhirq/core` and `@fhirq/themes`
name none. React, a peer of `@fhirq/react`, is yours to install and is not in
it. From M11, each release carries its SBOMs, with npm provenance and a
signed tag (NFR-X-07).

## Accessibility

The claim is WCAG 2.2 at A and AA. The [accessibility record](accessibility.md)
holds the evidence: what CI checks on every change, the script for the
manual screen-reader passes, each A and AA criterion with what checks it, and
[every known gap](accessibility.md#4-known-gaps).

**Its status is partial.** The automated gates pass on `main`. The three
manual screen-reader passes (NVDA with Firefox, JAWS with Chrome, VoiceOver
with iOS Safari) have **not been run yet**, and until they are the record
claims only what the automated gates show.

## Browser support

The published target (NFR-C-01) is the last two major versions of Chrome,
Edge, Firefox and Safari, and iOS Safari 16.4 or later. Not Internet Explorer
11 and not legacy Edge. The packages compile to ES2022 (NFR-C-06).

What CI runs is narrower than that target, and this table says where:

| Target | What CI runs |
|---|---|
| Chrome, Edge | Chromium 153, through Playwright 1.63: React 18 and 19, the element, accessibility, playground and docs site. Edge is not run separately |
| Firefox | Firefox 155, through Playwright: the element, accessibility, playground and docs site. The React adapter is not run in Firefox |
| Safari | WebKit 26.6, through Playwright: React 18 and 19, the element, accessibility, playground and docs site. This is Playwright's WebKit build on Linux, not Safari on macOS |
| iOS Safari 16.4+ | Not run. No test runs on iOS or on a WebKit as old as 16.4 |
| The previous major of each | Not run. CI tests the engine versions Playwright pins |

React 18 and 19 are both tested (NFR-C-03).

## Versioning and deprecation

- **Semver** (NFR-M-01): a breaking change only in a major release. A
  deprecation is announced at least one minor release before the removal.
- **All four packages share one version** (Changesets, fixed mode;
  ADR-0008), so `@fhirq/react` 1.4.0 always pairs with `@fhirq/core` 1.4.0.
  A package that depends on another pins it exactly.
- **The public surface is held by API reports.** Every change to it shows as
  a diff in the pull request, and CI fails without one (NFR-M-04).
- **Release tags say what is promised** ([`07-api.md` §1](07-api.md#1-rules-for-the-surface)).
  Before 1.0, a `@beta` symbol is documented and supported, but a change to
  it can land in a minor release. An `@alpha` symbol promises nothing. Today
  `@fhirq/core/view`, `@fhirq/react` and `@fhirq/element` are `@alpha`.
- **A saved snapshot restores on the same format major only.** A change to
  the snapshot format is a major release of `@fhirq/core` (ADR-0010,
  `05-architecture.md` A5). A snapshot is a way to resume a session, not a
  migration format: keep the `QuestionnaireResponse` as your record.

## Security reports

Report a vulnerability privately through GitHub's private vulnerability
reporting, never in a public issue. A report is acknowledged within 7 days,
and patched or publicly documented within 30 days (NFR-X-08). There is no
other support commitment (NFR-M-09). See the [security policy](../SECURITY.md).
